# 聊天文件附件设计

> 日期：2026-10-29  
> 项目：AI Chat Web  
> 范围：在聊天输入区上传 JPEG、PNG、GIF、PDF，并将后端返回的文件 ID 用于流式对话

## 1. 目标与范围

让用户能够在发送聊天消息时附加图片或 PDF。前端先上传文件到后端，随后将后端返回的文件 ID 写入流式聊天请求的 `fileIds` 字段，使后端能够将文件内容纳入模型上下文。

本次只支持 JPEG、PNG、GIF 和 PDF；不实现本地预览、拖拽上传、预签名 URL、文件删除回收或跨会话文件库。

## 2. 已确认的后端契约

- 上传接口：`POST /api/files`，请求为 `multipart/form-data`，字段名必须是 `file`。
- 上传成功响应的 `data` 含文件元数据，前端仅使用其中的 `id`。
- 流式对话接口：`POST /api/chat/sessions/{sessionId}/stream`，JSON 请求可选传入 `fileIds: number[]`，最多 10 个。
- 后端默认允许的单文件和单请求大小是 10 MB，前端使用同样的单文件限制作为即时反馈，后端仍为最终校验方。
- 图片附件需要模型返回 `supportVision: true`；PDF 不受该限制。
- 后端在首次关联附件后会从历史消息恢复附件。因此后续追问与重新生成无需再次传入 `fileIds`。
- 前端不得保存或拼接 MinIO object key、私有 URL 或文件内容。

## 3. 方案选择

采用**发送时上传**方案：`Composer` 管理本地 `File` 草稿，`useChatWorkspace` 在发送操作中按顺序上传全部附件，成功后再调用现有流式接口。

相较于选择即上传，该方案不会因用户放弃发送而产生孤立文件；相较于新增全局附件管理层，改动保持在既有 `Composer → useChatWorkspace → chatApi` 分层内。

## 4. UI 和交互

### 4.1 附件草稿

将输入区的“添加附件”占位按钮改为实际文件选择入口，并使用隐藏的文件选择控件限制可选 MIME 类型为 JPEG、PNG、GIF、PDF。

选中文件后，在输入框下方、底部工具栏上方显示附件卡片。每张卡片展示：

- 文件类型图标；
- 文件名；
- 格式化后的文件大小；
- 移除按钮。

用户可持续添加附件，最多保留 10 个。选择操作对每个文件独立校验：

- 不支持的类型拒绝加入并反馈原因；
- 单文件超过 10 MB 拒绝加入并反馈原因；
- 总数超过 10 个时，仅保留限额内的有效文件并反馈数量限制；
- 已保留的有效附件不因同批次的无效文件而被清除。

### 4.2 发送行为

`Composer` 发出文本和本地文件草稿。文本与附件可任意组合；因为后端要求 `content` 非空，只有附件而没有输入文字时，工作区使用 `请分析这些附件。` 作为请求和本地用户消息的内容。

点击发送后：

1. 若当前没有会话，复用既有逻辑先创建会话。
2. 若存在图片而当前已知模型不支持视觉输入，则提示切换模型，不上传、不创建消息、不发起流。
3. 逐个调用上传接口，按附件在界面中的顺序收集返回的文件 ID。
4. 全部上传成功后，创建本地用户和助手占位消息。
5. 调用流式接口，并在 `ChatRequest.fileIds` 中传入上传得到的 ID 数组。
6. 发起成功后清空文本和附件草稿，继续既有 SSE 读取和详情同步流程。

上传和发送期间，发送、添加和移除附件操作禁用；AI 生成期间保持现有停止按钮和重复提交防护。

## 5. 架构与职责

### 5.1 类型与 API

- `ModelSummary` 新增 `supportVision: boolean`，匹配后端模型列表字段。
- `ChatRequest` 新增可选 `fileIds?: number[]`。
- 新增 `UploadedFile` 前端类型，仅描述上传接口的响应元数据中前端需要的字段。
- `chatApi.uploadFile(file)` 用 `FormData` 发起 `POST /api/files`；字段名为 `file`，认证头沿用现有 API 客户端保存的动态 token 名称和值。

### 5.2 Composer

`Composer` 只管理待发送的本地文件：选择、校验、显示、移除与提交事件。它不调用 HTTP API，也不持久化文件 ID。

提交事件扩展为传递 `{ content, files }`。组件通过受控的清理信号或暴露方法，仅在工作区确认上传并开始发送后清空草稿。

### 5.3 useChatWorkspace

工作区负责：

- 上传编排与上传中状态；
- 图片模型能力的发送前校验；
- 附件默认提问文案；
- 仅在全部上传成功后创建本地消息、更新标题和开始 SSE；
- 将文件 ID 注入首次 `ChatRequest.fileIds`；
- 保持重试和重新生成不传 `fileIds`，依赖后端恢复历史附件。

## 6. 错误处理

- 文件选择校验失败：不加入无效文件，展示可理解的本地提示。
- 图片模型不支持：在上传前阻止发送，提示选择支持图片输入的模型。
- 上传失败：不调用流式接口、不创建本地用户或助手消息；保留全部文字和附件草稿，提示后端错误或“文件上传失败，请重试”。
- 上传全部成功后流式请求失败：沿用现有流式失败和会话详情同步处理；前端不删除已上传文件。
- 后端在请求建立前返回 JSON 错误、或建立 SSE 后返回 `FAILED` 时，沿用现有客户端错误解析和展示逻辑，以后端结果为准。

不新增上传文件的自动删除或垃圾回收逻辑；该行为由服务端文件策略决定。

## 7. 测试与验收

新增或更新现有 Node 测试，覆盖：

1. `chatApi.uploadFile` 使用 `FormData`、`file` 字段和动态认证头。
2. 带附件的提交先上传，再按上传成功顺序将 ID 传给 `ChatRequest.fileIds`。
3. 上传失败不会调用流式接口，不创建本地消息，并保留草稿。
4. 纯文本消息保持现有请求与行为。
5. 图片和不支持视觉的模型组合不会上传或发起流。
6. `Composer` 的选择、移除、文件数限制、文件大小限制、类型限制和附件-only 默认文案。
7. `npm run type-check` 与 `npm run build` 均通过。

完成后手动验证：选择 PDF 或图片、添加具体问题、发送、观察上传和流式回复；并确认服务端实际收到的是文件 ID 而不是文件内容或存储地址。
